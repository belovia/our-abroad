# Design

## Context

См. proposal.md, раздел Why. Сейчас `UserValidator.validatePassword` ставит `PASSWORD_REQUIRED`, если в строке нет текста, и на этом заканчивается. Тот же метод вызывается при создании пользователя и при смене пароля, до сравнения со старым паролем. Логин идёт через `AuthServiceImpl` и этот метод не вызывает. Тексты пяти конкретных ошибок уже лежат в `ErrorCode`. `PASSWORD_WEAK` нигде не ставится.

## Goals / Non-Goals

**Goals:**

- Одна проверка в `validatePassword` закрывает регистрацию, `POST /api/users` и смену пароля.
- Сообщение совпадает с уже заданным текстом `ErrorCode` и с порядком из delta-спеки `password-policy`.

**Non-Goals:**

- Не менять хеш уже сохранённых паролей и не заставлять логин отклонять слабый сохранённый пароль.
- Не требовать строчную букву и не начинать отдавать `PASSWORD_WEAK`.
- Не менять HTTP-код: сценарии по-прежнему отвечают `200` и `success: false`.

## Decisions

1. Правила живут в `validatePassword`, а не в каждом use case. Оба текущих вызова тогда получают одно поведение. Отдельный валидатор только для смены пароля дублировал бы порядок ошибок.
2. Проверки идут по шагам, а не одним регулярным выражением на весь пароль. Один шаблон не различает «короткий» и «запрещённый символ», а спека требует первое сообщение из фиксированного порядка.
3. Пароль не обрезается. Пробел — запрещённый символ. Строка из одних пробелов по-прежнему пустая для `StringUtils.hasText` и даёт `PASSWORD_REQUIRED`.
4. Длина считается через `String.length()`, как у `displayName` в том же валидаторе. Примеры в спеке укладываются в BMP.
5. Набор символов: латинские буквы, цифры и `@$!%*?&`. В классе символов эти знаки литеральны.

Альтернатива — отклонять любой слабый пароль общим `PASSWORD_WEAK`. Она отбрасывается: тексты уже различают причину, и спека фиксирует первое конкретное сообщение.

## Risks / Trade-offs

- [Клиенты, которые регистрировались коротким паролем, не смогут задать такой же новый] → Логин со старым паролем остаётся. В теме identity это записывается как действующее правило, GAP-002 закрывается после кода.
- [Успешный тест регистрации передаёт пароль `password`] → В том же изменении фикстура заменяется на пароль, который проходит правила. Сценарий с неверным email трогать не нужно: ошибка email возникает раньше.
- [`POST /api/users` и register расходятся, если править только один вызов] → Правка только `validatePassword`, оба пути уже его вызывают.

## Migration Plan

Схемы БД нет. Откат — вернуть прежнюю проверку «не пустой». Сохранённые хеши при откате не мигрируют.
